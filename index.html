GOMA-1015 TOPPERS/ASP3版シミュレータ（RTOS拡張版）

アーキテクチャ図・構成要素　｜　2026年8月26日 Step 10D 反映版　｜　夢・アーキテクティング工房 × Claude 共創研究
★ 核心原則：制御ロジックも物理モデルも すべて C 側（TOPPERS/ASP3）にあります。
Flask ブリッジは UDP↔HTTP の変換と観測値の集計だけを行い、制御の判断を一切持ちません。 asp を停止すると画面も止まることを実験で確認済みです（模擬ではありません）。

1. システムアーキテクチャ全体図

★ Step 10D の主な変更：温度制御を 1000ms → 100ms に細分化し、 プラントを 0.01 単位の累算器にして時間倍率を 1x／2x／5x／10x／20x の実行時可変にしました。 これにより保温の制御目標を仕様値（98／90／60℃）へ戻すことができ、表示と実装が一致しました。

2. メインループ方式との対比

★ Ch4〜Ch6 の共通層（要求・分析・設計モデリング MCP）は両方式で同一です。
異なるのは方式固有層のみで、GUI シミュレータの操作契約（HTTP API と画面）も可能な限り共通にしてあります。
観点メインループ方式（Flask版）RTOS方式（TOPPERS/ASP3版）
制御ロジックの所在Python（MILS 16ファイル）C（責務関数層・タスク層）
物理モデルの所在physics.py（Python側）hw_api_udp.c（C側）
時刻の駆動ブラウザが POST /api/tick（50ms × simSpeed）カーネルの周期ハンドラ（C側が自走）
速度変更可能（simSpeed をブラウザが持つ）可能（SPEED:n でC側の倍率を変更）
Python の役割制御・物理・API のすべてUDP↔HTTP 変換＋観測値の集計
スケジューリングループカウンタで手動管理CRE_CYC・優先度で自動管理

共有資源保護単一スレッドのため不要セマフォ4本（SEM_HEATER 等）

3. タスク・カーネルオブジェクト構成

3.1 タスク（CRE_TSK × 9）

タスク優先度起床契機実測の起床回数呼び出す責務関数
TASK_INIT1TA_ACT（起動時1回）—initSystem → ext_tsk
TASK_LID_EVENT2wai_flg(FLG_LID)0.0 回/秒handleLidEvent
TASK_MONITOR_WATER3slp_tsk ← 周期A 100ms10.0 回/秒monitorWaterLevel / monitorWaterSupply

★ 優先度と実行頻度は別概念です。優先度2の LID_EVENT は最も優先度が高いのに 0.0 回/秒、 優先度5の TEMP_CONTROL は 10.0 回/秒。優先度は同時に実行可能になったときの順序を決めるものであり、 どれだけ頻繁に動くかとは無関係であることが、画面上で対比して見えます。
★ ref_tsk は〔T〕【NGKI1217】でタスクコンテキスト専用です。周期ハンドラから呼ぶと E_CTX になります。
そのため観測専用の TASK_MONITOR（優先度16＝最低）を設け、観測が被観測系を乱さないようにしています。

3.2 周期ハンドラ・アラームハンドラ

★ 制御周期を 1000ms から 100ms へ細分化した理由：
ヒータOFF の判定は temp ≧ target で行われるため、行き過ぎは最大で1制御周期ぶん残ります。 1000ms 周期では 10倍速時に 1周期で 8.0℃ 動き、ミルク60℃設定で 65℃ まで上昇していました。 100ms 化により 1周期の変化は 0.8℃（20倍速でも 1.6℃）となり、制御目標を仕様値のまま運用できます。

4. 時間倍率

★ プラント内部は 0.01℃／0.01% 単位の累算器で動き、基準値に倍率を掛けます。
基準 PLANT_HEAT_BASE 8 = 0.08℃/100ms = 0.8℃/秒 は、1000W ÷ 300g ÷ 4186 の物理値そのもの（倍率1）です。
倍率加熱/tick実効20→100℃カルキ抜き制御1周期(100ms)の変化
1x8 (0.08℃)0.8 ℃/秒100 秒180 秒（仕様値）0.08 ℃
2x161.6 ℃/秒50 秒90 秒0.16 ℃
5x404.0 ℃/秒20 秒36 秒0.4 ℃
10x（既定）808.0 ℃/秒10 秒18 秒0.8 ℃
20x16016 ℃/秒5 秒9 秒1.6 ℃
★ カルキ抜きは KARUKI_COUNTS(speed) = 180 × 10 ÷ speed で算出します。 1800 / 900 / 360 / 180 / 90 といずれも整数になるため、 沸騰:カルキ抜き の比が倍率によらず保たれます。
倍率は 停止中のみ変更可能です。カルキ抜きの残りカウントは開始時の倍率で確定するため、 シナリオの途中で変えると残り時間が追従しません。
★ Step 10C までの経緯：この倍率は当初 PLANT_HEAT_RATE 8（＝ 0.8℃/100ms）として 10倍が定数に暗黙に焼き込まれており、GUI の速度ボタンは 5x を表示し、物理モデル欄は 0.8℃/秒（実装の 1/10）を表示していました。 UIラベル・表示値・実装値の三重の不一致で、設計文書とも要求仕様書とも照合できず、 実測ログの差分をとって初めて判明したものです。Step 10D で倍率を明示的な変数に格上げし、解消しました。

8. タスク観測のしくみ

★ 実測値：asp プロセス全体の CPU 使用率は 1% 未満（5秒間で累積 0.01秒）。 各タスクの1回の実行は 数十μs、ref_tsk の観測間隔は 200ms。 捉えられる確率は 約 0.03% であり、状態表はほぼ常に「待ち」に見えます。
これは異常ではなくRTOS の実像ですが、動いていることが画面から分かりません。
層担当内容
C（タスク層）goma1015_tasks.c起床直後に g_run_count[..]++（加算1回のみ）
C（テレメトリ）hw_api_udp.ctasks パケットに起床回数 c を載せる
Pythontoppers_bridge.pyC側の時刻で窓3秒の差分を取り、回/秒を算出
JavaScriptgoma1015_simulator.html算出済みの値を表示し、増えた行を600ms点灯
★ 被観測系は一切変えていません。タスクの周期・優先度・処理内容はそのままで、加算1回を足しただけです。
数える場所はタスクの起床直後です。責務関数の入口で数えると、タスクと責務関数が1対1でないため （TASK_MONITOR_WATER は2つ、TASK_WATER_SUPPLY は3つの責務関数を呼ぶ）、タスク状態表との対応がずれます。
回/秒の算出をブリッジ（Python）側に置いたのは、JavaScript ではブラウザ時刻と テレメトリ周期の食い違いにより値が倍化・欠落する問題が繰り返し起きたためです。 サーバ側なら実行して検証できます。

★ 責務関数層はこの境界を通じてのみハードウェアに触れます。SS2026 論文 3.1 節 「HW仮想化APIの境界の引き方が、組込み開発における生成AI活用の成否を決める」の実体です。

★ 「API境界は7本」と記述していましたが、hw_sim_set_water と hw_sim_set_temp は 当初ヘッダに宣言がなく実装ファイル内にのみ存在し、stimulus.c が直接呼んでいました。
Step 10D で hw_sim_get_speed を加え、実際に境界を越える経路は 10本になりました。 これは実機には存在しない治具であり、実機では倍率1に固定されて KARUKI_COUNTS(1) = 1800（100ms × 1800 = 180秒）＝ 仕様値そのものになります。

11. プラントモデル（hw_api_udp.c）

定数値倍率1での実効物理値との関係
PLANT_HEAT_BASE8（0.01℃/100ms）+0.8 ℃/秒1000W÷300g÷4186 = 0.8℃/秒 と一致
PLANT_COOL_BASE1（0.01℃/100ms）−0.1 ℃/秒自然放熱
PLANT_PUMP_BASE10（0.01%/100ms）−1 %/秒給湯による水位低下
PLANT_AMBIENT20020.0 ℃室温（固定）
PLANT_TEMP_MAX1000100.0 ℃相変化：常圧の水は100℃で沸騰し、それ以上上がらない
★ 相変化の実装は SS2026 の GL-9（Flask シミュレータで 107.8℃ を観測）と同一の対策です。
TOPPERS版でも当初は上限 105.0℃ で、シナリオ3で 104.2℃ を観測していました。 妥当域を「常圧・0〜100℃・液相」と明示化しています。
Step 10D で内部を 0.01 単位の累算器に変更したことで、倍率1（＝物理値そのもの）でも 丸め誤差なく積算できるようになりました。
